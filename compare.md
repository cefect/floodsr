# FloodSR Compared With a Bespoke Inference Notebook

| floodsr | bespoke research notebook |
|---|---|
| **Installability**: Distributed as the `floodsr` Python package with a CLI entrypoint. Basic CLI use is documented as `pipx install floodsr`; notebook use is documented as `pip install floodsr` in the kernel environment. | **Installability**: Usually cloned from a repository or copied from supplementary material, then repaired locally until imports, model code, and notebook cells run in the user's environment. |
| **Environment isolation**: Separates the default package path from the GDAL-backed extended path. Users can start with a basic install and only move to a conda-managed GDAL environment for large or VRT-dependent rasters. | **Environment isolation**: Often assumes the author's workstation, Colab image, or a broad `requirements.txt`. GDAL, CUDA, raster libraries, and notebook packages may be mixed in one environment. |
| **Python/runtime requirements**: Declares Python `>=3.12` and bounded runtime dependencies in `pyproject.toml`, including `onnxruntime`, `rasterio`, `geopandas`, `numpy`, and `tqdm`. | **Python/runtime requirements**: Requirements are often implicit in import cells. Version conflicts are discovered by running the notebook rather than by package metadata. |
| **User interface**: Provides stable commands: `floodsr models list`, `floodsr models fetch`, `floodsr tohr`, and `floodsr doctor`. The same CLI commands are used in terminal docs and tutorial notebooks. | **User interface**: Usually exposes a sequence of notebook cells. Users must understand which cells are setup, which are editable parameters, and which perform inference. |
| **Inference entrypoint**: `floodsr tohr` runs the end-to-end path from low-resolution depth raster plus DEM to high-resolution output. It supports a local DEM or `--fetch-hrdem` for Canadian HRDEM coverage. | **Inference entrypoint**: Typically calls model setup, preprocessing, tensor conversion, inference, and plotting across multiple cells. Reusing it on a new raster often requires editing paths and intermediate variables. |
| **Model artifact handling**: Uses `floodsr/models.json` as a manifest with model file name, URL, SHA-256 checksum, and description. `floodsr models fetch` downloads once, verifies checksums, and reuses the cache. | **Model artifact handling**: Model weights are often downloaded manually, pulled from drive links, or assumed to already exist at a path. Checksum validation and cache reuse are uncommon. |
| **Model/version selection**: Manifest versions are mapped to model worker modules. The current packaged model is `ResUNet_16x_DEM`, a 16x DEM-conditioned ResUNet backed by an ONNX artifact. | **Model/version selection**: The model version is often embedded in file names, notebook markdown, or checkpoint paths. Switching versions may require code edits. |
| **Input validation**: The CLI validates required inputs, mutually exclusive DEM modes, CRS policy, model artifact existence, model worker availability, and runtime tensor contracts. | **Input validation**: Validation is often whatever fails first in a cell: missing file, shape mismatch, CRS mismatch, or tensor error. Error messages may point at implementation details rather than user action. |
| **Geospatial workflow**: Keeps raster I/O, preprocessing, DEM handling, model workers, and engine runtime as separate package modules. Output defaults are predictable, and explicit output paths are treated as authoritative. | **Geospatial workflow**: Raster reads, reprojection assumptions, array manipulation, model calls, and output writing are often interleaved. This is flexible for exploration but harder to audit and reuse. |
| **Large raster behavior**: Supports shared tiling and mosaicking, with an in-memory path for modest extents and a raster-backed/windowed path for memory-constrained scenes. | **Large raster behavior**: Often demonstrates one small example tile. Scaling to full scenes may require new tiling, stitching, and memory-management code. |
| **Runtime backend**: Uses an engine abstraction with ONNX Runtime as the current implementation and CPU execution as the supported default provider. Runtime metadata is validated before inference. | **Runtime backend**: Often binds directly to PyTorch, TensorFlow, or ONNX Runtime inside the notebook. Provider/device assumptions may be scattered through setup cells. |
| **Diagnostics**: `floodsr doctor` reports package and backend status. Inference commands expose progress controls and are designed to report model/output diagnostics. | **Diagnostics**: Diagnostics are usually ad hoc print statements, plots, or notebook cell outputs. They may not be machine-readable or consistent across runs. |
| **Reproducibility**: Package metadata, manifest checksums, documented install tiers, tests, and release artifacts make the user-facing workflow repeatable. | **Reproducibility**: Reproduction depends on preserving the exact notebook state, data paths, package versions, and sometimes cell execution order. |
| **Automation**: A CLI-first design is easier to run from shell scripts, batch jobs, containers, or workflow managers after the model cache is prepared. | **Automation**: Notebook automation is possible, but usually requires `nbconvert`, parameterization, or extracting code into scripts first. |
| **Documentation**: Provides install, getting-started, user-guide, CLI reference, tutorial notebooks, and ADR-backed design decisions. | **Documentation**: Documentation is often the notebook itself. It can be excellent for explanation, but weaker as an operational reference. |
| **Best fit**: Operational and repeatable flood-raster enhancement where users want a supported install path, a stable CLI, cached model artifacts, and geospatial guardrails. | **Best fit**: Early research communication, model inspection, ablation examples, and interactive demonstration of how a published inference workflow works internally. |
